# Git Standards (reference)

The rules are split by purpose so that no text exists twice:

| Where | Owns |
|---|---|
| `.github/copilot-commit-message-instructions.md` | The **commit message contract**: format, types, scopes, subject and body rules, footers, breaking changes, accepted and rejected examples. Single source of truth. |
| `.github/copilot-pull-request-instructions.md` | The **pull request contract**: title format, description sections, required content. |
| `docs/DEVELOPER-GUIDE.md#git-standards` | The **process**: agent approval rule, a three-line summary plus a pointer to the contract, branches and integration, language. |
| `AGENTS.md#git-standards` | A six-line summary plus pointers, for agents. |
| `CONTRIBUTING.md#commit-messages` | A pointer for contributors. |

`docs/DEVELOPER-GUIDE.md` must never restate the type table or the examples: a second
copy drifts. When a message rule changes, edit the template of
`.github/copilot-commit-message-instructions.md` only.

## Why a dedicated file

VS Code registers it for the assistant that drafts commit messages:

```json
{
  "github.copilot.chat.commitMessageGeneration.instructions": [
    { "file": ".github/copilot-commit-message-instructions.md" }
  ]
}
```

The setting lives in `.vscode/settings.json`, generated by the skill, so the contract
travels with the repository instead of depending on each developer's user settings.

Two caveats worth stating in the generated repository:

- The setting is marked **Experimental** in the VS Code documentation. The file is
  therefore also linked from `docs/DEVELOPER-GUIDE.md`, `AGENTS.md`, and
  `CONTRIBUTING.md`, so it stays discoverable when the setting is inactive.
- Commit message generation is a VS Code feature of the editor; other harnesses read
  the same file only through the agent instructions that link it.

## Agent permissions

Git history is user-owned. An agent may read the repository history (`git status`,
`git diff`, `git log`, `git show`, `git branch --list`) and must never write to it on
its own: no `git commit`, `git push`, `git tag`, `git merge`, `git rebase`,
`git reset --hard`, `git clean`, no staging toward an unreviewed commit, and no
pull-request creation or merge. The agent prepares the change and the proposed
message; the user approves and saves it.

This rule is stated in `AGENTS.md#git-user-approved-changes-only` and referenced from
`docs/DEVELOPER-GUIDE.md#git-standards`.

## Concise commits in one paragraph

One logical change per commit; imperative subject, lowercase after the type, at most 72
characters, no trailing period; body only when the reason is not obvious, explaining why
rather than what; no `wip`/`temp`/`fixes`; no secrets or generated artefacts. Details and
examples live in the contract file.
