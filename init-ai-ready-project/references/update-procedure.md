# Update Procedure

How an already initialized repository is brought to the current skill standard when the
skill gains, changes, or drops a rule.

## Why markers exist

A repository generated by this skill mixes two kinds of text:

- **Project text** — values the user supplied (purpose, stack, commands, invariants) and
  the prose the templates fill from those values. It belongs to the repository.
- **Fixed text** — rules the skill owns: the English-only rule, the engineering
  principles, the Git standards, the design and test rules. It belongs to the skill.

Only fixed text can be updated automatically, so it must be identifiable without
guessing. Every fixed block is therefore wrapped, in the template and in every generated
file, by:

```
<!-- skill:block:<id> [attrs] -->
... fixed text ...
<!-- skill:end:<id> -->
```

The markers are the contract. Prose outside them is never rewritten by
`scripts/update.mjs`.

Not managed: `README.md`, `.gitignore`, `.vscode/settings.json`, and every section
whose body comes from a placeholder (`docs/PRODUCT.md`, `docs/USER-GUIDE.md`,
`docs/ADR.md`, `docs/GLOSSARY.md`, and the `{{...}}` sections of the other files). Those
are project content.

`.vscode/settings.json` is JSON: it cannot carry HTML markers, and a repository
usually already has editor settings. It is merged instead of updated — the two
generator settings are added only when the key is absent, and existing values are
never changed or removed. `update.mjs` performs the same merge.

A file that is nothing but managed blocks and carries no placeholder — currently the
two `.github/copilot-*-instructions.md` files — is created from the template when it
is missing, because it holds no project content to preserve.

## Anchors

When a marker is absent — a repository initialized by an older version of the skill —
the block is placed using the attributes on the begin marker:

| Attribute | Meaning |
|---|---|
| *(none)* | The block starts with a heading; if that heading exists in the target, its whole section is replaced |
| `after="<block id>"` | Insert the block right after that managed block — outside every region an update replaces, so the insertion survives |
| `before="<heading>"` | Insert the block before that heading line |
| `section="<heading>"` | Insert the block at the end of that heading's section |
| `replace="body"` | Replace everything after the first level-1 heading (used by `CLAUDE.md`) |

If the block's exact body already exists in the target, it is wrapped in markers
instead of being duplicated.

## Applying an update

```bash
node scripts/update.mjs --dest "<repo>" --dry-run   # inspect
node scripts/update.mjs --dest "<repo>"             # write
node scripts/check-output.mjs --dest "<repo>"       # verify
git --no-pager diff                                 # review
```

Reported actions:

| Action | Meaning |
|---|---|
| `updated` | An existing managed block was replaced with the current text |
| `adopted` | Unmarked text matched a block (exactly, or by heading) and is now marked |
| `inserted` | A new block was added at its anchor |
| `removed` | A marked block no longer defined by the templates was deleted |
| `unchanged` | The block already matches; nothing written |

The script is idempotent and reports `baseline OK` when nothing changes. It fails — it
never guesses — when a target file is missing, an anchor heading is absent, or the
templates themselves have unbalanced markers.

## Limits

- **Edits inside a fixed section are overwritten.** A repository whose fixed text was
  hand-edited, and that predates markers, loses those edits when the section is adopted.
  Report it before writing: `--dry-run` shows every `adopted` block.
- **Unmarked removed rules survive.** A rule that disappeared from the templates can be
  removed automatically only if the repository still carries its markers. Otherwise the
  script cannot tell it apart from project prose; point it out in the report.
- **Project rows inside a managed table are lost on adoption.** A doc-map row added by
  the project inside `agents-what-this-is` disappears when that section is adopted.
  Project-specific documents belong in the project-owned table below the block.
- **Deliverables are created only when they hold no project content.** A file that is
  nothing but managed blocks and no placeholder (today the two
  `.github/copilot-*-instructions.md`) is created from the template. Anything else that
  is missing is an error, never a silent scaffold — in particular `docs/USER-GUIDE.md`,
  which a repository initialized before it existed does not have: copy it from
  `assets/templates/docs/USER-GUIDE.md`, fill in its three placeholders, then re-run
  `update.mjs`.
- **`.gitignore` is never edited.** An older variant may exclude `.vscode/` as a
  directory, which defeats `!.vscode/settings.json` because Git cannot re-include a file
  inside an excluded directory. Check with
  `git check-ignore -v .vscode/settings.json` after the update and fix it by hand.
- **Prose outside blocks is not synced.** Guidance the templates add outside a managed
  block reaches only newly scaffolded repositories; for an existing one, add it by hand
  if the report says it matters.

## Maintaining the skill

When adding, rewording, or dropping a rule:

1. Edit the template, keeping markers balanced and one block per fixed unit. New rules
   that do not replace an existing section need an anchor attribute (`after=`,
   `before=` or `section=`), otherwise an old repository cannot place them. Prefer
   `after="<block id>"`: a heading anchor often sits inside another managed block, and
   the next update of that block would delete what was inserted.
2. Never put a `{{PLACEHOLDER}}` inside a managed block: an update would copy the
   placeholder into the repository.
3. Update [document-contracts.md](./document-contracts.md) and the `FIXED_CONTENT`
   expectations in `scripts/check-output.mjs`.
4. Verify both paths: `scaffold.mjs` on an empty directory, and `update.mjs` on a
   repository rendered by the previous template set. Both must pass `check-output.mjs`,
   and a second `update.mjs` run must report `baseline OK`.
